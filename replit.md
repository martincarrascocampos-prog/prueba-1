# FECh Plenario

Sistema de votación ponderada y gestión de sesiones plenarias para la Federación de Estudiantes de Chile (FECh).

## Run & Operate

- `pnpm --filter @workspace/api-server run dev` — run the API server (port 8080)
- `pnpm --filter @workspace/fech-plenario run dev` — run the frontend (port 18531)
- `pnpm run typecheck` — full typecheck across all packages
- `pnpm --filter @workspace/api-spec run codegen` — regenerate API hooks and Zod schemas from the OpenAPI spec
- `pnpm --filter @workspace/db run push` — push DB schema changes (dev only)
- `pnpm --filter @workspace/scripts run seed` — seed the database with admin + 93 members
- Required env: `DATABASE_URL`, `SESSION_SECRET`

## Stack

- pnpm workspaces, Node.js 24, TypeScript 5.9
- API: Express 5 + express-session + connect-pg-simple
- DB: PostgreSQL + Drizzle ORM
- Auth: bcryptjs + session cookies (httpOnly, sameSite lax)
- Validation: Zod (`zod/v4`), `drizzle-zod`
- API codegen: Orval (from OpenAPI spec)
- Build: esbuild (CJS bundle)
- Frontend: React + Vite + TailwindCSS + shadcn/ui + wouter + React Query
- Excel export: xlsx (SheetJS)
- QR codes: qrcode.react

## Architecture decisions

- Contract-first API: OpenAPI spec → Orval codegen → typed React Query hooks
- Voting weights frozen at vote time (`weight_at_vote` column in votes)
- Session attendance required before voting (enforced server-side)
- Concurrent vote protection via `INSERT ... ON CONFLICT DO NOTHING RETURNING id`
- `bcryptjs` used instead of `bcrypt` to avoid native module compilation issues
- Sessions stored in PostgreSQL via connect-pg-simple; `req.session.save()` called explicitly after login
- **Scaling for ~200 concurrent users (1 admin + ~93–200 members on one open session):** server emits are throttled per `(room,event[,topicId])` with a leading+trailing ~1s window (`throttledEmit` in `realtime.ts`); clients invalidate with a jittered 0–1000ms + coalesced delay (`src/lib/live-invalidate.ts`) to avoid a 200-client refetch stampede; the two hot fallback polls (topic results, speaking panel) were relaxed from 5s → 30s now that realtime is the instant path; `useSessionLive` does a jittered full invalidation on socket **re**connect to catch up on missed events; pg pool sized `max 20`, `idleTimeoutMillis 30000`, `keepAlive true`. Worst-case live latency ≈ 2s.
- **Deployment topology (required):** Socket.io rooms + the emit-throttle map are per-process singletons, so the app MUST run as a single instance — deploy as a **Reserved VM**, or pin **Autoscale to exactly 1 instance**. Multiple instances would split rooms and break fan-out.
- `evictUserFromSession` awaits every `RemoteSocket.leave()` — `.leave()` is async and callers emit right after, so an un-awaited leave races the emit and the evicted socket still receives it

## Product

- Admin (FECH/1906): create/open/close plenary sessions, manage vote topics, view real-time weighted results, export attendance + results + vote matrix to Excel
- Members (93 preconfigured, password 1234): mark attendance with session code, cast weighted votes (favor/contra/abstención), view personal vote history
- Histórico view: admin sees all sessions with their votations + weighted results + attendance summary; members see a personal history per session (attended/absent, own vote or "No votó"/"Ausente") plus the same aggregate results everyone sees
- Admin members list auto-refreshes (10s poll) so each account's current password stays visible in real time; admins can edit a member (name/username/group/faculty via `EditMemberDialog`, `PATCH /members/:id`), sort the list by name/username/group (client-side `localeCompare`), and delete a member via a Trash button + confirm dialog (`DELETE /members/:id`, requireAdmin). Delete is blocked for admin accounts and self-deletion.
- **Alternative voting weight:** each member has `votingWeight` and `votingWeightAlt` (both inline-editable in the members table). When creating a votación that is weighted AND estamento-restricted, the admin picks which column tallies it via a `weightSource` selector (`"normal"`|`"alt"`). The invariant is enforced server-side in `parseVotingShape` (topics.ts): `weightSource="alt"` only persists when `weighted && estamentos.length>0`, else forced to `"normal"`.
- **Account deactivation** (`active` flag on users): admins toggle via `ToggleActiveDialog` (`PATCH /members/:id {active}`). A deactivated member can still log in but the frontend `AuthGuard` shows a full-screen "Cuenta inhabilitada" state (can't reach vote/attendance pages); admins are never affected. On deactivation the server checks the member out of all open sessions they're actively attending (weight leaves every tally immediately) and evicts their live sockets. Profile + history are preserved. `AuthUser.active` is returned by `/auth/me`.
- **Live per-member ballot detail** (`TopicBallotsPanel`): `GET /topics/:id/ballots` (requireAuth — any logged-in member; `username` is nulled for non-admins since it doubles as a login identifier) returns every eligible member with their nominal vote/status (present|checkedOut|absent), sortable (grupo/nombre/voto) with absent+retired always sunk to the bottom, grouped Consejeros→CEE→COSEFECH. Admin can "Retirar de la sesión" (`POST /sessions/:id/attendance/:userId/checkout`). Used live in admin session-detail (realtime-invalidated via `use-session-live`), lazily (non-live, on accordion expand) in admin histórico per topic, AND read-only (no retirar/reingresar buttons) at the bottom of the member vote page (`member/vote.tsx`) so every pleno member sees the per-member vote detail live.
- **Retirados count as PRESENT** (attended-then-checked-out ≠ ausente): `/history/me` `attended` includes checked-out members; `/history/sessions` and `/public/history` `presentCount`/`presentWeight` use the union attendee∪checkedOut. **The retired-early distinction is ADMIN-ONLY:** public `attendees` list retirados as plain attendees (no `retiredEarly` field; modality preserved) and public ballots collapse `checkedOut`→`present` (`buildTopicBallots(..., {collapseRetired:true})`; `PublicBallot.status` enum is `present|absent`). Admin ballots panel/exports keep "Retirado". **Vote tallies are UNCHANGED** — `computeTopicResult` still excludes `checkedOutIds` weight from denominators.
- **Per-session frozen weights (`session_weights` table):** weight edits never retro-affect existing sessions. On session create the server snapshots every user's `voting_weight`+`voting_weight_alt` (`snapshotSessionWeights`); a late-created member joining an older open session gets a row at first attendance / admin mark-present (`ensureSessionWeightForUser`). All denominators/results/exports overlay the snapshot via `applySessionWeights`/`sessionWeightFor` (`api-server/src/lib/sessionWeights.ts`): attendance GET, votes results/ballots/weight-freeze/admin override, all history endpoints (via `sessionRoster`), and the 3 Excel exports. Missing snapshot rows fall back to current weight (keeps old tests working). Idempotent startup backfill (`backfillLegacySessionWeights`, called on listen) gives sessions with NO snapshot rows a synthetic one: Consejeros FECh = 0.75 (their original seeded weight, per user request for the 4 prod sessions), everyone else current weight. Prod data is fixed automatically on Publish (schema migrates + backfill runs at boot).
- **Session-scoped rosters (no retroactivity):** a member "exists" for a session only if `user.createdAt <= session.createdAt` OR they have an attendance row in it (`scopeMembersToSession` in `api-server/src/lib/roster.ts`). New members never retro-affect earlier sessions: totals/quorum/absentees in `/history/me`, `/history/sessions`, `/public/history`, live `GET /sessions/:id/attendance` (now 404s on missing session), topic results/ballots (`votes.ts`), and all three Excel exports (`admin.ts`, results/matrix now fetch the session row + 404). A late-created member can still join an OPEN older session — attendance marks them a participant, which re-includes them everywhere.
- **Public per-member ballots**: `/public/history` topics (`pasado` phase only) carry `ballots: [{name, group, status, voteLabel}]` (`PublicBallot` schema; built by `buildTopicBallots()` in history.ts, same labelFor summary format as admin views) — no usernames/weights. `public-home.tsx` renders them in a `<details>` collapsible per votación; retirados show "Se retiró antes · <voto>" (vote visible but not tallied).
- On member delete the user's DB row is removed (votes/attendance/speaking cascade), their active login sessions are purged from the connect-pg-simple `session` table, and their live sockets are force-disconnected (`disconnectUser` in `realtime.ts`) — deprovisioning is done at delete time, not via a per-request user-exists check (kept off the hot path for ~200 concurrent users)
- Real-time updates via Socket.io (path `/api/socket.io`, session-cookie auth, rooms `session:<id>` + per-user `user:<id>`): mutations emit `attendance:changed`/`session:changed`/`speaking:changed`, frontend invalidates React Query on events; polling kept as a 30s fallback. `attendance:changed` invalidates BOTH the ballots family AND the topic-results family (by URL prefix, jittered) so Retirar/Reingresar shifts weight and updates percentages + per-member "sin voto"/"ausente" instantly — not just the ballot status. Live-room join is scoped: admins may join any session; members may only join sessions they're actively attending (attendance row not checked out). This is intentionally stricter than REST view (which stays open so members can discover/join sessions). The member dashboard re-emits `join`/`leave` after marking attendance / self check-out. The member vote page and admin LiveSessionPanel both mount `useSessionLive` for instant tally/attendance sync (`TopicResults.sessionId` gives the vote page its session id); those hot polls relaxed to 30s.
- **Per-user access channel** (`access:changed` on room `user:<id>`, `emitUserEvent`): every socket joins its own `user:<id>` room; admin actions that change one member's access emit here because the member is often NOT in the session room at that moment (just evicted, or never attending). Emitted on BOTH directions — loss-of-access (checkout, mark-absent, account deactivate) AND grant-of-access (mark-present, attendance reactivate, account reactivate). `useUserLive` (always mounted in `AuthGuard`) invalidates `/auth/me` so the "cuenta inhabilitada" screen flips instantly; `useSessionLive` also re-`join`s + refreshes so a re-admitted member resubscribes. No jitter (fan-out of 1). New `emitUserEvent` callers must be added to the `vi.mock("../lib/realtime")` in route tests or the route 500s.
- "Vista de Sesión" global view shows who currently holds the floor with a synced countdown; speaker (and collective consejeros) see a "Tienes la palabra" banner
- Speaking system ("Sistema de Palabra"): members can only "pedir la palabra" while an admin has opened the "ronda de palabras" (`speakingRoundOpen` flag on the session; admin toggles via `POST /sessions/{id}/speaking-round`, requireAdmin). **Opening a round requires selecting an agenda point** (`speakingRoundAgendaPointId` on the session): the admin picks a "punto de tabla" when opening, and member self-requests are server-scoped to that point (the member form shows the active point read-only, no picker). Closing the round clears the point. When the round is closed the member request form is disabled (amber notice) but the speaker queue stays visible. In the admin "Agregar oradore" form, choosing Categoría="Estudiante de Base" hides the member search and forces free-name entry (base students aren't registered members). The branch is decided server-side by `req.session.rol`, so a member can't bypass the gate via request body. "Palabra colectiva" aggregates the WHOLE consejero group of a Unidad Académica (by group + faculty, present or not) and sums their speaking minutes — the frontend builds the faculty list from all members, not just present ones.
- User-facing topic noun is "moción"/"Moción propuesta"; voting-action labels ("Votar ahora", "Boleta de Votación") and the login system descriptor ("Sistema de Votación Ponderada") are intentionally kept as-is.
- **Voting types per votación** (configured on the create-topic form in admin session-detail): `type` = `"mocion"` (favor/contra/abstención) or `"candidato"`. `detail` is an optional free-text description shown under the título on the ballot + results. Candidato **defaults to single** (`candidateMode "single"`: pick ONE candidate + abstención); `candidateMode "multiple"` ("Voto de opciones múltiples") is opt-in via a Switch. **Multiple mode is approval-style, NOT cumulative:** a voter may pick AT MOST ONE vote per candidate (up to `votesPerVoter` distinct options); unused picks count as **abstención** (the server auto-fills the remainder, the client only sends selected candidates each with `count:1`). The member ballot models this as a `Set` (`multiSelected`/`toggleCandidate` in `vote.tsx`) and the confirm button stays enabled reading "Confirmar (N como abstención)". `weighted` toggles weighted vs flat (1 vote = 1). Server treats all candidato voting as allocation-based (single = one allocation of count 1) and enforces max-1-per-candidate + abstención remainder server-side. `estamentos` (string[]) restricts eligibility "por estamento" — empty set = Pleno completo (all attendees). Eligibility = attendance + estamento membership; `eligible: false` shows a "No habilitade" state on the ballot.
- **Unidades académicas catalog** (`unidades_academicas` table, CRUD via `unidades.ts` — `GET/POST/DELETE /unidades`, requireAdmin for writes): managed from the admin members page (`UnidadesManager` component above the members table; duplicate name → 409 toast). The "palabra colectiva" picker in the speaking panel builds its Unidad Académica list from this managed catalog (with live consejero counts) instead of scraping faculties off member rows.
- **Reingresar** (admin ballots panel): alongside "Retirar de la sesión" (checkout), a checked-out member can be re-admitted via "Reingresar" (`POST /sessions/:id/attendance/:userId/reactivate`, requireAdmin) — their weight re-enters every tally.
- **Editar votaciones** (admin session-detail, `EditVotesDialog`): a button below "Editar asistencia" opens a (wide, `max-w-4xl w-[95vw]`) dialog to override each member's vote on an existing votación — **both mociones AND candidato (single + multiple)**. Backed by `PUT /topics/:topicId/ballots/:userId` (requireAdmin, `AdminBallotInput`) which branches by topic type: **moción** takes `{option: "favor"|"contra"|"abstención"|null}` (`option` required — missing property → 400 so a malformed body can't silently clear; explicit `null` clears); **candidato** takes `{allocations: VoteAllocation[]|null}` (`allocations` required — missing → 400; explicit `null` clears; else same rules as a real vote: single = exactly `votesPerVoter` allocations, multiple = approval max-1-per-candidate with abstención remainder auto-filled server-side). Both paths share `buildCandidatoRows()` with the member `POST /vote` handler so override rules never drift. The tx deletes the member's existing ballot+votes then, unless clearing, inserts a fresh ballot+vote(s) with weight frozen from the topic's `weightSource` column. Member must be `active` + estamento-eligible; invalid candidate ids (e.g. from another topic) → 400. Works on open OR closed topics (admin corrections). Emits `emitVotesChanged`; the dialog invalidates the ballots + topic-results families so tallies update live. `GET /topics/:id/ballots` returns per-member `allocations` (candidato only, includes `candidateId:null` abstención rows) so the editor pre-selects the current ballot.
- **Public pre-login page** (route `/`, no AuthGuard, `PublicHome`): a transparency portal for the student body. Multicolor gradient hero "Sistema Plenario FECh" (no "Historial" title) + a fixed blurb explaining the Sistema Plenario, then three phase-grouped sections: **Plenos activos** (live meeting link + attendance roster), **Próximos plenos** (upcoming cards with prominent link), **Detalle de plenos pasados** (accordion: weighted results + attendance roster + acta download). Backed by unauthed `GET /api/public/history` which now returns **ALL sessions** classified by `phase`: `activo` (status `abierta`), `futuro` (status `cerrada` + `scheduledAt` in the future), else `pasado`. Each session carries an **attendance roster** — `attendees` `[{name, group, modality: online|presencial}]` + `absentees` `[{name, group}]` — populated for `pasado`/`activo` only (never `futuro`). **Vote tallies (`topics`) are exposed for `pasado` only** — active/future publish no live results. Still strips internal `actaObjectPath` (nulled; `hasActa` boolean) and streams actas via `GET /api/public/sessions/:id/acta` (closed + stored-path guarded). Member display names + group + modality ARE intentionally public here (transparency); usernames/passwords/weights/per-member vote rows are NOT. An "Ingresar" button routes to `/login`; the login page has a "Panel público" back button routing to `/`. Route `/` is the app's default (public portal), NOT login. **`AdminHistorySession` is shared with admin `/history/sessions`; the new `phase`/`attendees`/`absentees` fields are OPTIONAL and only the public route populates them.**
- **Estamentos are a FIXED set of divisions** (no CRUD, no `/admin/estamentos` page, no catalog table): the create-votación form offers exactly three chips mapping to `users.group` values — CEE (Delegades), Consejerías (`"Consejeros FECh"`), and Cosefech (`"COSEFECH"`). **Mesa Directiva is intentionally excluded.** The allowed set is whitelisted server-side (`ALLOWED_ESTAMENTOS` in `topics.ts` = `["CEE","Consejeros FECh","COSEFECH"]`); any other value sent as an estamento is silently dropped. The `topic_estamentos` join table is kept for per-votación eligibility.
- Candidato results render via `CandidateResultsBar` (weighted tally per candidate + abstención/sinVoto/ausente); moción results via `ResultsBar`. `TopicResults.weights/percentages` are optional (only present for moción); guard with `?`. History `myVote` for candidato is a summary string like "Ana ×2, Beto ×1" — `MyVoteBadge` renders non-standard values as-is (no uppercase).
- QR codes displayed for session codes; attendance entry form for members
- **Inasistencia Justificada** (admin-only label, `justified_absences` table keyed session+user): set from the admin "Editar Asistencia" dialog's Ausentes section ("Justificar"/"Quitar justificación" via `PATCH /sessions/:id/attendance/:userId {present:false, justified:true|false}`); marking present clears the flag. It is a LABEL ONLY — no attendance row exists, so the member counts as absent for quorum, denominators, and vote eligibility everywhere. Displayed in: admin attendance dialog (amber chip, `AttendanceList.justifiedIds`), public portal absentee chips (`PublicMemberRef.justified`), member "Mi Historial" badge (`MemberHistorySession.justified`), and the Excel attendance export (estado "Inasistencia Justificada"). Never selectable by members in "Marcar Asistencia".
- **Fallback polling is socket-aware:** `TopicBallotsPanel` polls 30s only when the socket is NOT connected (`useRealtimeStatus`); admin dashboard/history polls relaxed 15s→30s. Realtime push remains the primary update path.

## Gotchas

- The PostgreSQL `session` table must exist. `createTableIfMissing: true` in connect-pg-simple may not create it reliably. Create it manually: `CREATE TABLE IF NOT EXISTS session (sid VARCHAR NOT NULL PRIMARY KEY, sess JSON NOT NULL, expire TIMESTAMP(6) NOT NULL); CREATE INDEX IF NOT EXISTS IDX_session_expire ON session (expire);`
- Always call `req.session.save()` explicitly after login — async session stores may not persist data before the response is sent otherwise
- `trust proxy` must be set to `1` always (not just in production) since the app runs behind Replit's reverse proxy in both dev and production
- Export hooks (`useExportAttendance`, `useExportResults`, `useExportMatrix`) are React Query **queries**, not mutations — call the raw `exportAttendance()`, `exportResults()`, `exportMatrix()` functions directly on button click
- Sessions start with status `"cerrada"` — admin must explicitly open them before members can mark attendance or vote
